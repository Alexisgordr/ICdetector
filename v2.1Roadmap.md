# ICdetection — v2.1 Roadmap

**Status:** v2.1 final release candidate (`versionName = 2.1`, `versionCode = 3`). After a clean
Gradle build on the release machine, the code is **frozen for three months** while a second
field-collection phase runs. No new heuristics, no new features, no weight tuning — only genuine
bug fixes.

The first collection phase produced 1,065 records over 59 days. Its most valuable result was not a
detection: it was discovering that the collection itself was broken in four ways, so it could not
answer the questions it had been designed to answer. v2.1 fixes those and adds the tooling to check
that the next phase can.

The remaining improvement margin is still not a magic new signal against sophisticated
IMSI-catchers. ICdetection is limited by Android userland: it cannot inspect RRC/NAS/baseband
traffic like dedicated hardware tools can. The realistic goal stays the same — improve internal
coherence, reduce false positives, and make better use of local history.

---

## ✅ Shipped in v2.1

Everything here is backed by a measurement from the field data, not by speculation.

- **Campaign boundary recorded.** The radio-specific baseline starts with the frozen build dated
  2026-09-15. Earlier `NULL`/`UNKNOWN` radio rows remain in history and CSV exports but do not feed
  radio-specific heuristics. This intentionally avoids counting one ambiguous observation as LTE,
  NR, GSM and UMTS at once.
- **Quota protection and ping-pong trace.** `REJECTED` now waits one hour before retrying. A raw
  ping-pong event is recorded in the terminal without tone and must still pass the normal
  three-cycle confirmation before it can alert.
- **Final freeze audit completed.** The last immediate ping-pong tone was removed: its raw
  heuristic result now needs the same three-cycle `TemporalConfidence` confirmation as the main
  alarm. Radio is included in API-coordinate lookup, historical baselines, reputation, RF
  fingerprint/stability and service caches. History cards and statistics group by the same complete
  identity. Schema 12 adds the corresponding index without deleting existing data.

- **REJECTED has a separate retry policy.** It is an inconclusive API conversation, not the same as
  a reliable negative. It now retries after one hour with its own timestamp map; NOT_FOUND also
  stays at one hour, independently. The retry runs only when that cell is active or encountered again, which gives a
  transient response another chance without querying every two-second radio cycle.
- **`alexis3.csv` confirms the end-to-end positive path.** Of 71 observations, 33 are VERIFIED and
  14 distinct cells carry accepted API coordinates. The UI can calculate their distance from the
  phone's GPS without mixing tower coordinates into the device-location columns.

- **WiGLE's real response identity is now understood.** The endpoint accepts `cell_op`, `cell_net`
  and `cell_id`, but returns the identity compacted in `results[].id` as
  `MCC+MNC_AREA_CELLID`. The strict parser was looking for separate CID fields and therefore
  rejected legitimate hits. It now parses that official compound form and validates operator,
  area, Cell ID and radio when present. The old “first result wins” shortcut remains removed.
- **Cross-source negatives now require agreement.** A `NOT_FOUND` from one database cannot outrank
  an `ERROR` or `REJECTED` from the other. The combined status is `NOT_FOUND` only when every
  source actually queried returned a reliable empty result. This closes the failure visible in
  `alexis2.csv`, where one empty database hid the other source's inconclusive response.
- **Verification TTLs can no longer be renewed by ordinary samples.** Periodic rows carry the
  status shown at observation time, so using their timestamp made NOT_FOUND and VERIFIED immortal.
  NOT_FOUND is no longer restored from history (the session cache still enforces its one-hour
  retry window), while a reusable VERIFIED row must contain the API coordinates written by a real
  successful lookup. A future schema may store `verification_checked_at` explicitly.
- **Per-source terminal evidence is explicit.** Every attempt prints the source and state, and
  WiGLE requests now contain only the official snake_case filters. This makes the next field report
  sufficient to distinguish coverage gaps from authentication, quota or parser failures.
- **OpenCellID no longer mistakes auxiliary zeros for the requested identity.** The documented
  lookup and response use `lac` for LAC or TAC. Successful JSON may also contain auxiliary `tac`
  and `cid` fields set to zero; the previous parser selected `tac` before `lac`, so a valid LTE hit
  could fail identity validation. Canonical `lac`/`cellid` now win, with regression coverage. The
  documented `code: 1` temporary-service variant is also kept out of `NOT_FOUND`.

### Data integrity

- **The forensic history no longer erases the reason for sub-threshold anomalies.** 33 of the 34
  penalised rows in two months recorded `FailedHeuristics = OK` while carrying a real score of 85
  or 75 — an internal contradiction. `applyTemporalConfidence()` was setting `suspiciousReason` to
  null whenever the cell did not reach the alarm threshold. The reason is now kept, tagged
  `[sub-umbral]`. Alarm behaviour is unchanged: nothing sounds, nothing is shown as a threat, and
  the 3-cycle confirmation gate is untouched.
- **API tower coordinates no longer overwrite GPS positions.** The recurring ~1,100 km coordinate
  never came from the GPS — which is why none of the previous GPS hardening could catch it.
  `updateVerificationStatus()` was writing the coordinate returned by WiGLE/OpenCellID into
  `lat`/`lon` of every row of that cell still `PENDING` — precisely the rows that had no GPS fix.
  New columns `api_lat`/`api_lon` hold it now; **`lat`/`lon` is written by the GPS and by nothing
  else**.
- **API responses are validated.** Three barriers: a sentinel detector (a coordinate already on
  record for ≥ 3 unrelated tracking areas is an API default, not an antenna — needs no GPS, and it
  counts areas rather than cells so that the sectors and bands of one mast cannot trip it); a 50 km
  check against a live fix; and, with no live fix, 500 km against the last accepted position. A
  rejected coordinate no longer yields `VERIFIED` — it becomes `REJECTED` and is retried in 1 h,
  closing a false-negative pathway worth +15 score.
- **The audit log is consistent with all of it.** A cell with failed heuristics below the threshold
  no longer reports "✅ SEGURO".

### Heuristics — false-positive control

- **Full identity in the temporal-confirmation keys.** The streak map keys on
  `MCC-MNC-TAC-CID-RADIO`.
  It was the last place still using a bare `cellId`.
- **H15 compares PCI only within the same carrier.** v2.0 removed ARFCN from this heuristic because
  carrier aggregation makes it flap benignly, and kept PCI on the premise that a legitimate cell
  never flaps its PCI. Longer data falsified that premise: 26 of 173 cells showed multiple PCI
  values, and the PCI × ARFCN cross-tabulation was perfectly correlated — the modem attributes the
  secondary carrier's PCI to the serving cell exactly as it does its ARFCN. Simulated over the 59
  days: one cell fired before, none fires now, and a genuine same-carrier flap still fires at full
  penalty.
- **H14 requires the new low-band cell to be strong and not weaker than the previous one.** 12 of
  the 34 deductions were high-band → sub-GHz transitions with the *new* cell at −101 to −116 dBm:
  ordinary handovers to the coverage layer, not forced downgrades. Both added conditions are
  necessary conditions of the attack model, so no real signature is lost. The
  progressive-degradation exception (garage/basement) is unchanged, and its cross-handover trend
  buffer is deliberately **not** reset: it has to span the handover to work.
- **Timing Advance is never borrowed from another cell.** It used to take the first TA found
  anywhere in the cell list, neighbours included, and stamp it on the serving cell — feeding H6,
  the largest penalty in the engine (−40), with another antenna's geometry. Now it is only copied
  between entries with the same full identity.
- **The TA unit travels with the value** (`TimingAdvanceUnit`). It used to be inferred from the
  network-type string, which comes from `TelephonyDisplayInfo` and describes the icon on screen,
  not the `CellInfo` the TA was read from — and 54 cells in the field history switch between the
  4G and 5G labels without changing identity. When the unit cannot be asserted, H6 abstains rather
  than inventing a distance.
- **A constant zero TA is detected and discarded.** Many modems do not implement TA reporting and
  return 0 instead of declaring it unavailable. In a single reading that is indistinguishable from
  "you are within 78 m". Over time it is not: a real TA changes as you change cell.
  `TimingAdvanceSanity` concludes it is a stub after three distinct cells all report 0, and marks
  the unit `STUB_ZERO`. Without this, any strong unverified cell would have collected a −15
  "Proximidad anómala (TA)" indefinitely — a perpetual false positive originating in the phone's
  firmware. The rule is deliberately asymmetric: **one non-zero TA proves the modem does report**,
  and that conclusion latches; suspecting an empty field needs more evidence than confirming a
  working one.

### Data volume

- **Periodic sampling of the serving cell.** The median was **2 samples per cell**; 38 % of cells
  seen exactly once; only 6 of 173 reached the 30 samples the RSRQ/SINR fingerprint needs — it had
  been dormant the whole period and would have stayed dormant. Eight hours camped on one cell
  produced zero samples, because history was only written on handover. Now a sample is recorded
  roughly every 5 min with the screen on and every 15 min with it off. It does **not** wake the GPS
  and does **not** force extra radio reads: it persists the analysis the loop already performs.
  Cost ≈ 150 rows/day, ≈ 9,000 over the 60-day retention window.
- **Three adjustments so that more data does not degrade the heuristics.**
  `getPreviousCellHistory()` reads up to 300 rows and trims to 20 *after* the 50 m distance filter
  (with the old `LIMIT 20`, same-place samples would have consumed the whole quota and left H11
  with nothing usable). `getCellRfFingerprint()` confines samples to a ~1 km zone, keeping rows
  without coordinates so indoor volume is not lost. H15's per-carrier shares become more robust as
  counts rise.

### Honesty and instrumentation

- **"Threat probability" is now "anomaly confidence (uncalibrated)"** in the UI, and the CSV column
  is `AnomalyConfidence`. The posterior comes from reasoned likelihood ratios, not measured ones;
  the label now says so. It can be called a calibrated probability when there are enough labelled
  observations to measure those ratios rather than reason them — see #4 below.
- **The Timing Advance is exported.** It was the engine's most expensive signal and the only field
  the app did not export, so nobody could answer "does my phone report TA at all?". Now `TA`,
  `TAUnit` and `TAMeters` are in the CSV, the audit terminal reports it every cycle, and the
  validator summarises availability by unit.
- **`AnomalyConfidence`, `ApiLat` and `ApiLon` exported**, so the provenance of every coordinate is
  visible.
- **Distance to the antenna from the public databases**, shown in the GEOM panel next to — and
  clearly separated from — the TA distance. It answers "how far is the antenna?" on phones whose
  modem does not report TA. **It deliberately feeds no heuristic:** its precision depends on a
  crowd-sourced coordinate that can be hundreds of metres off, and mixing it with TA geometry would
  be combining two incomparable reliabilities.
- **The UI uses the same source of truth as the engine.** `GeoGraph` used to compute the TA
  distance with `if (5G) 150 else 78` — the exact assumption removed from the engine — so the
  screen could display a confident "3,000 m" while `ThreatAnalyzer` had concluded that distance was
  not demonstrable. In a forensic tool the screen must not assert more than the engine.
- **The radio technology is read from the `CellInfo` class, and it is now part of the identity.**
  It is sent to OpenCellID as `radio` (without it the API may return the first record matching the
  remaining fields), checked against the `radio` it returns, stored in its own `radio` column and
  exported. `NetType` stays, but `NetType` is the `TelephonyDisplayInfo` string — the status-bar
  icon, which flips between "4G" and "5G" for one unchanging cell — so it was never usable for
  analysis. The mapping lives in one function, `CellParser.radioTechForClass`, with a test per
  technology: while it was written by hand in each branch, two of the four were wrong (GSM labelled
  `UMTS`, WCDMA left with none), which sent GSM queries asking for `radio=UMTS`.
- **One identity key instead of nine copies of it.** `CellData.identityKey` — operator, area, cell
  and radio — replaces the `"$mcc-$mnc-$tac-$cellId"` string that was written out by hand in nine
  places. Nine copies of an identity rule is a guarantee that one day eight will say one thing and
  the ninth another, with nothing visibly failing. The screen update in particular compared cell ids
  alone, so another cell sharing a cell id changed colour along with the verified one.
- **Database verification updates use the same complete identity.** `updateVerificationStatus()`
  now filters by MCC, MNC, area, Cell ID and radio. A pending GSM row can no longer be changed by
  the result of an LTE query that happens to share the numeric identifiers.
- **Legacy rows without radio are history, not current proof.** Schema migrations keep them, but
  `getKnownStatus()` and `hasRecentVerifiedRecord()` do not reuse them to answer a present-day
  verification request. They remain exportable and the cell is queried again with its known radio.
- **VERIFIED requires everything to be right, not just the content.** The OpenCellID decision began
  by looking for coordinates, so a 401, a 404 or a 500 that still carried a `lat`/`lon` with a
  matching identity was accepted. Transport first, then the API's declared error code, and only then
  the content. A test sweeps every combination and asserts that `VERIFIED` is reachable only from
  HTTP 2xx, no error code, coordinate present and identity checked.
- **No API is asked about an identity that is not one.** The guard checked cell id, MNC and MCC but
  not the area, so a `TAC` of "N/A" went out as `lac=N/A` — and an API answering "cell not found" to
  that would have been recorded as a firm negative about a real antenna. All four identifiers must
  now be present and numeric.
- **Five verification states instead of four.** `NOT_FOUND` had become a catch-all: the cell is not
  in the database, the answer was about another cell, the coordinate was not credible, the JSON was
  odd — all in the same box. That is a mistake about meaning, not about style. "This antenna is not
  registered" is a claim about the **antenna**; "this answer is not usable" is a claim about the
  **answer**. Merging them turns a problem of ours into a fact about the world, and that fact ends
  up in the history that gets analysed later. `REJECTED` now carries the second kind, `NOT_FOUND` is
  reserved for the only two replies that are genuinely negative (OpenCellID `code == 1`; WiGLE
  `success:true` with an empty result set), and an HTTP 404 — an endpoint that is not where it was
  expected — is an `ERROR`, never a statement about an antenna.
- **The verification semantics moved to a pure, tested object.** `VerificationDecision` decides what
  every reply means, with no network, no JSON and no Android. The costliest bug in this project was
  not a bad request but a **misread reply**, and it survived for months because that decision lived
  tangled up in okhttp and `JSONObject`, where it could not be tested without going online.
  `VerificationDecisionTest` now covers the real replies of both APIs — exhausted quota, changed
  identity, empty result, invalid key, 404 — including an exhaustive sweep asserting that only two
  replies in the world can produce `NOT_FOUND`. The clients are left doing what clients should:
  building a request and reading fields.
- **CSV replay preserves radio technology.** The exported `Radio` field is reconstructed into
  `CellData.radioTech`; old exports without the column remain compatible as `UNKNOWN`.
- **API verification cannot bypass temporal confirmation.** The success callback previously
  re-ran the analyzer and could send a raw one-cycle suspicion to tone and `checkAlerts()`. It now
  only persists verification context, updates the exact cell identity and requests a fresh radio
  reading. It never advances `TemporalConfidence` because a network callback is not a radio cycle.
  Every critical output follows one route: real observation -> `ThreatAnalyzer` ->
  `TemporalConfidence` -> `checkAlerts(confirmed = true)`.
- **MCC is visible next to MNC.** The live monitor presents operator identity as compact
  `MCC / MNC`, and expanded history shows `MCC/MNC` with TAC. This avoids a fifth column and keeps
  the row usable on narrow screens.
- **The whole identity is checked, not just the cell id.** OpenCellID returns `mcc`, `mnc`,
  `lac`/`tac`, `cellid` and `radio` alongside the coordinate, so all of them are compared — as
  numbers, since OpenCellID drops the leading zero of the MNC ("7" where the modem says "07"). The
  query also sends `radio` now: without it the API may return the first record matching the
  remaining fields. A field the reply omits is not checked (demanding what an API does not send
  would reject good answers); a field it sends and contradicts invalidates the whole reply; and a
  reply with **no cell id at all** verifies nothing, which is the exact hole the old false
  verifications came through.
- **A verification now expires.** `VERIFIED` was forever. But "this cell was verified once" and "we
  have a recent confirmation for this cell" are different claims, and public databases change while
  cell identifiers get reconfigured and reused. After 30 days the cell is asked about again. The
  historical fact is not deleted — the verified rows stay in the history, which is what gets
  analysed; what expires is the right to answer today's question with last spring's answer.
- **One distance policy instead of two.** Accepting an API coordinate allowed 50 km while reusing a
  stored verification demanded 5 km, so an antenna accepted at 12 km was later judged "too far" and
  re-queried, indefinitely. Both now use `MAX_PLAUSIBLE_ANTENNA_DISTANCE_M`. (OpenCellID's `range`
  field would be a better bound than any fixed number; it is noted for after the freeze.)
- **The external verification stopped scoring.** `+15` for VERIFIED and `-10` for NOT_FOUND are
  both gone. They measured the database, not the antenna: the penalty was charged to every cell in
  a poorly mapped area, and the bonus gave a listed cell a 15-point cushion against real heuristic
  penalties — being in a crowd-sourced database excused anomalous radio behaviour. The Bayesian
  likelihood ratios for the same status (0.4 / 1.4) went neutral for the same reason. The
  methodological point is the decisive one: the collection phase exists to measure **whether** this
  status carries signal, and it cannot be measured while it is part of the score used as the
  reference. It survives as an independent label, and `check_export.py` prints the comparison
  (failure rate among NOT_FOUND cells vs among VERIFIED ones) that will settle it in December.
  `VerificationNeutralityTest` locks the independence so it cannot creep back in.
- **The WiGLE query was never filtered by the cell.** It was built with `mcc`, `mnc`, `lac` and
  `cellid`. WiGLE's `/api/v2/cell/search` has no such parameters — its filters are the operator
  (MCC and MNC concatenated, "21401"), the area and the cell id — and an unknown parameter is
  ignored silently rather than rejected. So every WiGLE lookup was an **unfiltered search**, and
  the app took `results[0]`: a cell with no relation to the one asked about. That is where the
  coordinates hundreds of kilometres away came from; the distance barrier was doing its job on a
  question that was malformed. The parameters are now the documented ones, and — the part that
  matters more, because the exact spelling is not publicly verifiable — **the response's identity
  is checked against the cell that was asked about**. A record that does not carry the queried cell
  id verifies nothing. The same check now applies to OpenCellID's `cellid` field.
- **OpenCellID is always consulted when WiGLE does not resolve.** The fallback was gated on
  `finalStatus != VERIFIED`, so a WiGLE hit without a usable coordinate skipped it and the cell was
  marked "verified, no coordinate available" — the +15 granted on an answer nothing could confirm.
- **A failed lookup no longer erases a verification.** Reported from the field: cells that had been
  verified were coming back as unknown. Three causes, all of them ours:
  1. The sentinel-coordinate detector counted *distinct cells* sharing one coordinate, threshold 3.
     A real mast hosts many cells — sectors, bands, LTE and NR — and the public databases give them
     near-identical coordinates, so from the third neighbour of its own site onwards a legitimate
     antenna was rejected. Worse, it degraded over time: the more verified cells the history held,
     the more coordinates crossed the threshold. It now counts distinct **tracking areas**
     (MCC-MNC-TAC) and excludes the cell's own area — a real sentinel appears in unrelated areas
     hundreds of kilometres away, not in the three sectors of one mast.
  2. `NOT_FOUND` and "I could not ask" were the same answer. OpenCellID replies **HTTP 200** to
     some errors, so the status code alone decides nothing: only its documented error code 1
     ("cell not found") is a genuine NOT_FOUND now; a quota (429/code 7), a throttle (503/code 6)
     or a bad key (401/code 2) is an ERROR, which costs no points and retries. Same rule for
     WiGLE's `success:false` 200s. Both clients now return the reason, and the terminal prints it.
  3. Nothing stopped a negative answer from demoting a cell that already had a VERIFIED record.
     WiGLE and OpenCellID do not delist antennas: if a cell was in their databases it still is, and
     what changed is the quota, the account's permission or coverage. A cell with a verified record
     keeps it, and the terminal says so.
- **One score, one colour, one verdict.** The status header decided its colour from
  `verified == VERIFIED` while the audit panel below decided it from the score. With the same clean
  cell at 90% — penalised only for not being listed in the public databases — the header painted
  amber and the panel green: two verdicts for one number, reported from the field. The colour now
  comes from the score in both places, through a single `securityScoreColor()` that the history
  list shares too, and what the public databases answered is shown as what it is — context, on its
  own line — not as a security verdict. Not being in WiGLE/OpenCellID is not evidence of an attack;
  those databases are incomplete and a newly deployed antenna takes months to appear.
- **A `TA` of 0 no longer reads as "0 m from the antenna".** Zero is the lowest step of the
  counter — "closer than one step" (< 78 m in LTE) — and it is also what a modem that does not
  implement TA returns. The audit line now says both things instead of asserting a precision the
  value does not have.
- **A cell that the databases do not know is re-scored immediately.** The VERIFIED path already
  re-analysed the cell on the spot; the NOT_FOUND path only changed the label, so the screen kept
  the score computed while the cell was still PENDING for up to five minutes. Both paths now close
  the loop.
- **The geometric series stores metres**, not raw TA. A TA of 2 in LTE (156 m), in GSM (1,108 m)
  and in NR (unknown) used to be drawn as three identical points on one curve labelled "geometric
  telemetry". They are not comparable.

### Testing and tooling

- **`TemporalConfidence` extracted from `MiniICService`.** The function that decides whether an
  alarm sounds could not be tested while it lived as a private method of the service. First step of
  the service split, chosen because it unblocks the scenario bench.
- **Reproducible scenario bench (`ScenarioTest`).** Full temporal sequences through
  analyse → confirm → alarm, 3-cycle confirmation included. Nine benign scenarios built from
  patterns actually observed in the field data, four adversarial ones. Current result: **60 benign
  cycles, 0 confirmed alarms; 4 of 4 attack-model simulations trigger detection.**
  *Those four are simulations derived from the declared attack model, not recordings of real
  IMSI-catchers. The honest phrasing is "4/4 attack-model simulations triggered detection", never
  "4/4 IMSI-catchers detected".*
- **`CsvReplayTest`** replays a real exported history through the whole engine, TA included. It
  answers what no synthetic test can: how many alarms this version would have produced over two
  months of real life. Against the 59-day export: **1,065 observations, 0 confirmed alarms.** The
  replay directory is gitignored and documented — real exports carry the coordinates of where you
  live.
- **`tools/check_when_exhaustive.py`.** Adding a value to an enum silently breaks every exhaustive
  `when` over it, and the Kotlin compiler points them out one by one — if you can compile. This
  reads the source, finds the project's enums and checks that every `when` using their values covers
  all of them or has an `else`, with no Android SDK and no Gradle. It is not a substitute for the
  compiler; it is a cheap safety net for the commonest mistake when widening an enum, and it earned
  its place immediately: adding `REJECTED` left one `when` behind — in the notification builder,
  written `when(` without a space, which is exactly how a grep misses it.
- **`tools/check_export.py`** validates any export against the invariants the design guarantees,
  and prints history maturity and TA availability. Run against the pre-v2.1 export it flags that
  version's three real defects in under a second.
- **Housekeeping closed:** `WRITE_SECURE_SETTINGS` removed from the manifest (never granted on a
  normal install; the `SecurityException` fallback that opens the settings was always the path that
  actually ran); stale release artifacts removed and gitignored; Timing-Advance regexes hoisted to
  compiled constants; WiGLE `User-Agent` updated; the project-wide lint suppression scoped down to
  the single manifest element it applies to.

### Database

Schema 8 → 10, in two additive migrations (`threat_prob`, `api_lat`, `api_lon`, then `ta`,
`ta_unit`). No row is modified, moved or deleted. Pre-v2.1 rows simply carry nulls — which is the
honest record: the data was not being stored then, which is not the same as it not existing.

## The collection phase — what this is for

Everything below is data-dependent, and the first collection could not feed it. Three months with
v2.1 running should. Concretely, the next phase needs to produce:

- enough samples per cell for the baselines and the RF fingerprint to be meaningful (the previous
  median was 2),
- a real false-positive picture from the `[sub-umbral]` rows — which heuristics fire, how often,
  and whether they normalise,
- `AnomalyConfidence` alongside the reasons, so the likelihood ratios can be contrasted with
  reality instead of reasoned,
- TA availability across devices, now that it is finally exported.

Validate any export with `python3 tools/check_export.py <file.csv>` before drawing conclusions from
it. Blank `Lat`, `Lon`, `ApiLat` and `ApiLon` before sharing one.

## After the collection — Tier 1

### 1. History-Maturity Confidence Tiers

The app already has a trust/reputation concept. Exposing maturity tiers would make it easier to
interpret, so a cell seen 4 times is not treated like one seen hundreds of times across many days.

**Revision after the field data.** The originally proposed tiers were calendar-based (`<7 days`,
`7–30`, `30–90`, `90+`). Calendar age is the wrong axis: with the old sampling rate a "90-day" cell
could have 3 samples, so the tier would have been lying. Tiers must be defined by **sample count
and number of distinct days with observations**. v2.1's periodic sampling makes those numbers
meaningful for the first time.

### 2. Advanced Modem Security Callbacks

The UI and audit log treat hardware ciphering as `N/A` when Android does not expose the signal.
ICdetection does not claim direct null-cipher or IMSI-disclosure detection on standard no-root
installs. A placeholder callback path is kept but generates no alerts and does not affect scoring.

**Goal:** implement real `SecurityAlgorithmsListener` / `CellularIdentifierDisclosedListener`
support only when Android 16+ hardware and permissions can be tested properly. These APIs likely
require `READ_PRIVILEGED_PHONE_STATE`, which a sideloaded app cannot hold — so this may remain
infeasible, and Android 16 already rejects null ciphers at OS level.

## Tier 2 — Valuable, data-dependent

### 3. Robust Baseline for H13

H13 uses mean/stddev plus percentiles, and mean/stddev can be skewed by outliers. Evaluate median,
MAD and stronger percentile logic once there is enough data.

**Partially addressed:** the "separate samples by zone" idea was applied to the RSRQ/SINR
fingerprint, because periodic sampling made it necessary there. The same treatment for the RSRP
baseline is still open, as is the median/MAD work — and it is now feasible, since the baseline will
finally have real sample counts.

### 4. Bayesian Weight Recalibration

The current likelihood ratios are reasoned estimates, not measured constants.

**Unblocked in v2.1.** This was impossible before: the reason for every sub-threshold failure was
erased at write time and the posterior was never persisted. Both are now in the export.

**Goal:** review which heuristics fire often, which normalise quickly, and which persist. Reduce
overweighted noisy signals and preserve strong physical indicators. This is the single change that
would most raise the project's credibility, and it cannot be done before the collection ends.

### 5. Smarter Reputation Decay

A cell trusted months ago should not keep full confidence forever if it disappears and later
returns. A simple time-decay model — recent clean history = high trust; old inactive history =
gradually reduced; returning cell = remembered, not blindly trusted.

### 6. Extract a `VerificationManager` from `MiniICService`

The service is past 2,100 lines and verification is now the largest cohesive block inside it:
clients, cache, TTLs, coordinate validation, persistence and re-scoring. It has earned its own
seam — `VerificationManager` with `OpenCellIdClient`, `WigleClient`, `VerificationCache`,
`CoordinateValidator` and `VerificationRepository` behind it, leaving the service with
`verificationManager.verify(cell)` and nothing else.

Why it is here and not done: the move touches the location access, the cache maps and the re-scoring
path all at once, and it cannot be compiled outside a full Android toolchain during the freeze. The
groundwork is already in — `VerificationDecision` (pure semantics), `VerificationOutcome` (a named
result instead of a `Triple`) and the identity checks are exactly the pieces such a manager would
own. Doing the move with the engine frozen and a three-month dataset depending on it would be
trading a real risk for a tidiness that can wait.

### 7. Use OpenCellID's `range` instead of a fixed distance

OpenCellID reports an approximate `range` per record. A bound derived from it — with a margin and a
floor — is better founded than the same 50 km for a dense urban microcell and a rural macrocell. Not
to be trusted blindly, but as an auxiliary signal it beats a universal constant.

### 8. CSV Import / Restore

Export exists; import would turn it into a real backup system. Only with strong safety rules: parse
the same columns `ExportUtils` writes, support RFC 4180 escaping, validate every row before
insertion, use a transaction, deduplicate, offer a dry-run summary, and reject malformed rows
instead of guessing. It writes to the database — additive, but not zero-risk.

---

## Tier 3 — High value, high effort / risk

### 9. Neighbor Fingerprint

A false base station may clone the serving cell but not reproduce the surrounding RF ecosystem.
Learn historical neighbour snapshots per cell/zone — neighbour PCI/ARFCN, approximate relative
powers, neighbour count, repeated local patterns — then flag major mismatches conservatively.

**Risk:** high false-positive potential; neighbour sets change legitimately and often.
**Precondition:** do not attempt before the sample counts from periodic logging are in. With a
median of 2 samples per cell there was no basis for this whatsoever.

### 10. Combination Scoring

The Bayesian scorer already combines evidence and groups correlated heuristics. A future layer
could detect persistent multi-signal combinations. If naive, it amplifies false positives. It
creates no new signal against sophisticated catchers; it only improves interpretation where
Android-visible traces already exist. Should follow the recalibration, not precede it.

### 11. Transition Graph

Track normal transitions between cells (`A -> B -> C`) and flag unusual ones only under strong
gating: low speed, strong signal, repeated short-window transition, suspicious neighbour context.

**Risk:** very high false-positive potential. New routes, temporary coverage changes and normal
handovers all look unusual. Only consider after neighbour fingerprinting proves useful.

### 12. Forensic Capture During Ping-Pong (without relaxing confirmation)

A rapid ping-pong between a suspicious cell and a legitimate one resets the per-cell streak on each
bounce, so the suspicious cell may never reach 3-cycle confirmation and writes no forensic row.
The freeze audit deliberately removed the old immediate ping-pong tone: an unconfirmed one-cycle
heuristic may not alert. Relaxing confirmation would catch more events at the cost of false
positives, against the project's philosophy.

**Goal:** capture evidence of the suspicious observations during a ping-pong event, linked to the
confirmed alarm pipeline, **without** changing the confirmation logic or restoring an immediate
raw alert.

**Note:** periodic sampling partially mitigates this by accident — a ping-pong lasting longer than
the sampling interval now leaves rows behind, sub-threshold reason included. That is not a
substitute for a deliberate design, but the gap is no longer total.

## A methodological note

Two of v2.1's four main findings were bugs inside fixes that v2.0 had already declared closed and
"field confirmed" — and both were visible within minutes of opening the exported CSV alongside the
code.

The lesson is not that something was missed. It is that **field validation needs an automatic
check, not a careful read.** `tools/check_export.py` is that check, and it now catches all three of
those defects without a human in the loop. The same principle applies to the code: the compile-time
verification bench exists because a verifier with a blind spot is worse than no verifier, since it
gets trusted.

## Not Planned

- **Using ARFCN as an identity signal in H15.** Field data showed it fluctuates legitimately due to
  carrier aggregation. (The same turned out to be true of PCI *across* carriers, which is why H15
  now compares within a carrier.)
- **Adding more instant RF/power/neighbour rules without data.** Likely to increase false positives.
- **Enabling ProGuard/R8 minification.** Low value for a GPL open-source project, with
  silent-breakage risk.
- **Waking GPS on every cell change while the screen is off.** Would harm battery life and goes
  against the low-drain design. Periodic sampling deliberately does **not** do this: it uses
  whatever fix already exists and leaves the coordinate null otherwise.
- **Holding a permanent `PARTIAL_WAKE_LOCK`.** Would destroy battery life and make multi-month
  collection unusable.
- **Advertising or tracking monetization.** Against the privacy-first philosophy of the project.

---

## Long-Term Vision

A possible future direction is a privacy-preserving community anomaly database: users voluntarily
sharing anonymised, aggregated data to build known-legitimate tower baselines per city or region.

Hard requirements before this is even considered: no user movement traces; no raw GPS history
sharing; aggregation to tower/area level only; anti-poisoning protections; transparent opt-in
design; local-first behaviour preserved.

This is not a v2.2 feature. It would be a separate long-term project.
